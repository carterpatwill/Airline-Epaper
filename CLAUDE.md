# Project Goal — "Closest Plane Overhead" e-paper dashboard

## The goal
A **self-contained physical device** that shows the single aircraft currently
**closest to the user overhead** — its route (where it's coming from / going to),
altitude, ground speed, heading, aircraft type + silhouette, and a "where to look
in the sky" hint (compass direction + elevation angle).

**ALL logic runs on the device.** No companion server, no image streaming. The
device connects to WiFi, calls the flight APIs itself, computes the closest
plane, and draws the UI natively to its own e-paper panel.

## Target hardware — Seeed Studio reTerminal E1001
- 7.5" ePaper, **800×480**, **monochrome / 4-level grayscale**
- **ESP32-S3 + 8MB PSRAM**, 32MB flash, **2.4GHz-only WiFi** / BT 5.0, USB-C,
  ~3-month battery, microSD (≤32GB FAT32), temp/humidity sensors, buzzer.
- Displays natively-drawn graphics; there is no browser and no HTML on-device.
- Ships with **SenseCraft** firmware; our custom Arduino firmware **replaces** it.
- **Full spec, hardware overview, expansion pinout, and Mac flashing notes:
  see [HARDWARE.md](HARDWARE.md).** The ePaper SPI pins are NOT documented in
  the wiki — pull them from the schematic PDF / Seeed Arduino example.

## Architecture (all on-device firmware)
1. **WiFi connect** on wake.
2. **Fetch telemetry** — HTTPS GET OpenSky `/states/all` for a bounding box
   around the device's fixed lat/lon. Parse JSON, filter to airborne, pick the
   nearest by haversine distance.
3. **Enrich** — HTTPS GET adsbdb `/v0/callsign/{cs}` (route) and
   `/v0/aircraft/{icao24}` (type). Cache in RTC/NVS memory across wakes.
4. **Compute** — climb/descent from vertical rate, compass bearing, and
   elevation angle = atan(altitude / ground distance).
5. **Render** — draw the card directly to the e-paper with graphics primitives
   + fonts + a pre-converted silhouette bitmap for the aircraft base model.
6. **Sleep** — deep-sleep between refreshes (e-paper is slow; **1–5 min** cadence)
   to hit the multi-month battery target.

## Firmware stack (DECIDED)
- **Arduino-ESP32** — for arbitrary HTTPS + JSON + custom layout (ESPHome/
  SenseCraft are too constrained for this logic).
- **Graphics: GxEPD2 + Adafruit_GFX fonts** — direct e-paper drawing, 4-gray,
  low RAM. (LVGL considered and rejected as overkill for a single card.)
- **HTTPS**: `WiFiClientSecure` (TLS; start with `setInsecure()`, pin CAs later).
- **JSON**: `ArduinoJson` with a filter to keep the OpenSky array small.
- Flash from the browser via the **Seeed reTerminal E-Series Firmware Hub**
  (desktop Chrome/Edge, USB-C), or Arduino IDE / `esptool`.

## Firmware source layout (firmware/src/)
Split by concern (each folder is on the include path via `platformio.ini`
`build_flags`, so `#include "foo.h"` resolves without a folder prefix):
- `main.cpp` — lifecycle only: `setup()`/`loop()`, the fetch→draw `runCycle()`,
  deep sleep, and the button handling.
- `core/` — `board.h` (pin map + DEBUG/GALLERY flags), `config.h` (user
  settings/secrets), `types.h` (`Plane`/`Weather`/`Screen`/`Airport`),
  `state.*` (shared `g_plane`/`g_weather`/`g_screen`).
- `display/` — the shared GxEPD2 `display` object + `displayInit()`.
- `geo/` — haversine/bearing/compass/elevation + the airport arrival inference
  (`AIRPORTS[]` table lives here).
- `net/` — WiFi, `httpGetJson()`, OpenSky OAuth (`getOpenSkyToken()`), the PSRAM
  allocator, and the on-screen fetch diagnostics (`g_httpCode` etc).
- `data/` — `flightdata.*`: OpenSky `fetchNearest()`, the flash aircraft DB
  (`acdbInit()`/lookup), type/airline/logo lookups, adsbdb fallbacks, weather.
- `ui/` — all e-paper drawing (details card, map screen, gallery, status).
- `generated/` — machine-made headers (`gen_*.h`); regenerated by `tools/build_*`.
  Do NOT hand-edit.

## Role of the existing files (reference/prototype only)
- `dashboard.html` — **the visual spec** for the on-device layout (800×480,
  black-on-white, 4-gray-safe, silhouette + stats + "look" footer). NOT deployed;
  it exists so we can preview the design in a browser. Firmware must reproduce
  this layout with native drawing.
- `tracker.py` / `base_models.py` / `plane-images/` — the **Python prototype** of
  the exact API calls, closest-plane logic, and type→silhouette mapping the
  firmware must reimplement. `plane-images/*.png` are the source art to convert
  into embedded monochrome/4-gray bitmaps.

## Design constraints (keep the panel happy)
- Monochrome-safe: black/white + at most the 4 gray levels; never rely on color
  or anti-aliasing to convey information. Dither images, don't gradient.
- High contrast, hard rule lines, large legible type. Fixed 800×480 layout.

## Watch out for (ESP32 gotchas)
- OpenSky & adsbdb are **HTTPS** → TLS required; mind heap during handshake.
- OpenSky `/states/all` can be large → always use the bounding-box query and an
  ArduinoJson filter so parsing fits in RAM.
- OpenSky anonymous access is rate-limited → back off / cache; consider a free
  account for higher limits.
- Cache route/type lookups in NVS so we don't re-hit adsbdb every wake.

## Gotchas already solved (don't re-debug)
- OpenSky over TLS + ArduinoJson streaming = `IncompleteInput`. Fix: buffer the
  whole HTTP body into PSRAM (heap_caps_malloc SPIRAM), THEN deserialize from
  memory. Also `useHTTP10(true)` + `Accept-Encoding: identity` to avoid
  chunked/gzip. See `httpGetJson()` in firmware/src/net/net.cpp.
- Large OpenSky doc parsed with a PSRAM allocator for ArduinoJson (PsRamAllocator).
- Serial debug is dead on the USB port -> diagnostics go on-screen.
- Wake button is NOT a wake source in our firmware; only the timer wakes it.
- **LittleFS mount**: `LittleFS.begin()` defaults to a partition labelled
  `"spiffs"`, but ours is `"littlefs"`. MUST call
  `LittleFS.begin(false, "/littlefs", 10, "littlefs")` or it silently fails to
  mount (symptom: on-screen `DB 0`). See acdbInit() in firmware/src/data/flightdata.cpp.
- **uploadfs reliability**: a 29MB LittleFS partition made `pio run -t uploadfs`
  drop the CH34x connection mid-erase ("Serial data stream stopped"). Fix: sized
  the partition to 16MB (DB is ~14MB) in partitions_e1001.csv — reliable write in
  ~2min. Also, USB auto-reset for `-t upload` is flaky; if it fails to connect,
  do the BOOT dance (hold BOOT, tap RST, release BOOT) when "Connecting..." shows.
- **The "company" airline name comes from the CALLSIGN prefix** (gen_airlines.h,
  baked into firmware), NOT the flash DB. The flash DB (acdb.bin) uniquely adds
  the TAIL NUMBER + offline aircraft TYPE. Private/GA planes show no company by
  design (owner field dropped to stay flash-only, no SD).
- **Destinations**: aircraft do NOT broadcast destination over ADS-B. adsbdb's
  callsign->route lookup is a stale schedule DB and is often wrong (verified:
  a SkyWest touching down at SNA showed adsbdb "MSP->MSN"). So for a plane that
  is low (<10000ft) + descending near a known airport, we OVERRIDE the dest with
  the nearest airport (geometric ground truth = it's landing there) and mark it
  "(landing)". adsbdb is only trusted for cruising planes / origin. Airport
  table = MAJOR commercial only (SNA/LAX/LGB/ONT/BUR) in firmware/src/geo/geo.cpp.
  GA fields (Fullerton/Chino) deliberately excluded — a jet on SNA final passing
  over the Fullerton GA strip is landing at SNA, not there. Inference also requires
  the plane's track to point AT the airport (arrivalAirport(), 70deg tolerance) so
  transiting/passing planes aren't falsely tagged. Add major airports as needed.
  No free keyless API gives real live destinations; don't go hunting for one.

## Data sources
- OpenSky Network — live position/altitude/speed/heading. **OAuth2 client-
  credentials** now (Basic auth retired): POST client_id/secret to the Keycloak
  token endpoint for a 30-min bearer token; pass `Authorization: Bearer`. Creds
  in config.h, token cached in RTC. Standard tier = 4000 credits/day; our ~2.5
  sq° box costs 1 credit/request. See getOpenSkyToken() in firmware/src/net/net.cpp.
- **On-flash aircraft DB (offline, no key, no SD)** — the OpenSky metadata CSV
  (`aircraft-database-complete-2025-08.csv`, 616k rows) is preprocessed by
  `tools/build_ac_db.py` into: `firmware/data/acdb.bin` (14 MB sorted binary,
  icao24→typecode+registration, binary-searched from LittleFS) plus generated
  headers `gen_aircraft_types.h` (typecode→friendly model + silhouette id) and
  `gen_airlines.h` (callsign prefix→airline). Airline = live callsign's 3-letter
  ICAO prefix (UAL→United), NOT the DB's owner (that's a lessor half the time).
  Upload the .bin with `pio run -t uploadfs`. Refresh monthly by re-running the
  script + uploadfs. This is now the PRIMARY source for aircraft type.
- adsbdb.com — route (origin→destination). Aircraft type only as a FALLBACK
  when the flash DB misses (newer airframe not in that month's snapshot).

## Bulk-fetch nearby routes (free-tier strategy — PLANNED, not yet built)
Goal: better origin/destination than adsbdb while staying **100% free**, no
metered-bill risk. Core idea (Carter's): don't look up planes one at a time —
fetch ALL nearby flights + their routes in ONE request and cache them all, so
one request serves many planes.

- **API: airlabs.co `/flights?bbox=south,west,north,east`.** A single request
  returns every flight in the box with `lat,lng,alt,speed,dir,hex,flight_iata,
  dep_iata,arr_iata,aircraft_icao` — i.e. position + origin + destination + type
  for ~20–50 nearby planes at once. (FlightAware `/flights/search -latlong` also
  does bbox but bills per 15-record page → metered/expensive in a busy SoCal box.
  Wrong tool. airlabs is the one. Free tier ~1,000 req/mo — CONFIRM exact quota +
  which fields are gated when signing up; needs a free API key, no card.)
- **Why it stays free — sweep on cache MISS, not per wake.** Requests scale with
  how often you sweep, not with plane count. When the closest plane overhead is a
  cache miss, do ONE bbox sweep and cache dep/arr/type for EVERY nearby plane by
  callsign. Arrivals cluster on the same corridors, so that one sweep pre-caches
  the next several planes. Est. ~5–15 sweeps/day = ~150–450 req/mo → fits the
  ~1,000/mo free tier with headroom. (Per-plane lookups would be ~20–100/day.)
- **Design:**
  1. Every wake: OpenSky bbox (free, keyless) → positions + closest plane +
     callsign. Fast-changing, no quota spent.
  2. Look up that callsign in the NVS route cache.
  3. On cache MISS only: one airlabs bbox sweep → cache all nearby routes/types.
  4. Fallbacks when airlabs quota is gone / plane missing: adsbdb (keyless) +
     the geometric airport override on approach.
- **Caveats:** airlabs dep/arr is still schedule-derived (destination isn't
  broadcast — same limit as adsbdb), so KEEP the geometric override for planes on
  approach; it's ground truth. Cache entries keyed by callsign, evict after a few
  hours. This shares the NVS cache with the adsbdb caching TODO above.
